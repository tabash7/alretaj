الإجابة المختصرة

مكتبة vercel-labs ui، واسمها في README «UI SDK»، مكتبة سلوكيات يستخدمها الوكلاء الذكيون لبناء واجهات المستخدم. تشمل السلوكيات التنقل بلوحة المفاتيح والتركيز والتحديد والإغلاق والنوافذ المنبثقة والسحب والإفلات وخصائص ARIA، وتعيش في @ui-sdk/core مع محوّلات لخمسة أطر: React وVue وSvelte وSolid وWeb Components. المكتبة في مرحلة beta، لذلك تُجرَّب في مشروع منفصل قبل الاعتماد عليها.

قد تطلب الإدارة إضافة حقل بحث بسيط إلى لوحة داخلية، فيه زر مسح، ويعمل بلوحة المفاتيح، ويعلن عن نتائجه لقارئات الشاشة. تبدو المهمة صغيرة، لكنها تتطلب الانتباه إلى التركيز والإغلاق عند الضغط على Escape وخصائص ARIA. عندها يبرز سؤال معقول: هل توجد مكتبة تحمل هذه السلوكيات جاهزة؟

يشرح هذا المقال شرح مكتبة vercel-labs ui بخطوات واضحة: ما تحلّه المكتبة، وكيف تُثبَّت وتُجرَّب، وكيف تعمل مع الوكلاء البرمجيين، وما قيودها ومخاطرها. كما يعرض معايير الترخيص والصيانة والأمان التي ينبغي فحصها قبل أي قرار، ومتى لا تكون هذه المكتبة الخيار المناسب.

ما هي مكتبة vercel-labs ui وما الهدف من إنشائها؟

يعرّف مستودع vercel-labs/ui نفسه بأنه مكتبة سلوكيات للوكلاء الذكيين، تُستخدم لبناء الجيل التالي من واجهات المستخدم. وفي ملف README يظهر المشروع باسم UI SDK. المستودع مكتوب بلغة TypeScript، ويحمل ترخيص Apache-2.0.

الفكرة الأساسية أن كل مكوّن يُبنى من سلوكيات جاهزة، بدلاً من كتابة كل سلوك من الصفر. يذكر README أن التنقل بلوحة المفاتيح، والتركيز، والتحديد، والإغلاق، والنوافذ المنبثقة، والسحب والإفلات، وخصائص ARIA اللازمة لها، موجودة في الحزمة @ui-sdk/core. وإن لم يكن مفهوم الوكيل واضحاً بعد، فاقرأ ما هو الوكيل الذكي المستقل ودورة عمله قبل المتابعة.

مثال افتراضي للتوضيح: لدى شركة في الرياض بوابة داخلية فيها حقل بحث يظهر في ثلاث شاشات. بدلاً من أن يعيد كل فريق كتابة سلوك زر المسح وإعادة التركيز إلى الحقل، يُعرَّف السلوك مرة واحدة، ثم يُعرض في الإطار الذي يستخدمه الفريق. هذا مثال توضيحي لا يمثل عميلاً فعلياً.

ما الذي يقوله المستودع عن نفسه؟

تُظهر لقطة المستودع 5791 نجمة و196 شوكة. هذه أرقام تتغير مع الوقت، لذلك راجع صفحة المستودع مباشرة قبل أي قرار. الأهم من الأرقام ما يصفه README عن بنية المكتبة:

  • @ui-sdk/core: السلوكيات وخصائص ARIA المشتركة.
  • موصِّلات (adapters) لـ React وVue وSvelte وSolid وWeb Components.
  • أوامر التثبيت تبدأ بـ npm install @ui-sdk/react @ui-sdk/core، مع استبدال الحزمة حسب الإطار المستخدم.

ماذا تعني حالة beta للفريق؟

يصف README المكتبة بأنها في مرحلة beta، وأن الإطار والواجهات البرمجية والتوثيق والسلوك قد تتغير قبل الإصدار العام، وأنها تخضع لشروط beta الخاصة بـ Vercel.

عملياً، تعامل مع أي تجربة اليوم على أنها قابلة للتغيير، لا أساساً دائماً لمنتج.

تنبيهقبل التجربة

لا تُدخل المكتبة في مشروع إنتاجي قبل مراجعة شروط beta، وتحديد خطة لتحديث الكود عند تغيّر الواجهات البرمجية.

ما المقصود بـ«السلوكيات» للوكلاء الذكيين في هذه المكتبة؟

يصف مستودع vercel-labs/ui المكتبة بأنها مجموعة سلوكيات للوكلاء الذكيين، تُستخدم لبناء واجهات المستخدم من الجيل التالي. وبحسب README، تشمل هذه السلوكيات التنقل بلوحة المفاتيح، والتركيز، والتحديد، والإغلاق، والنوافذ المنبثقة، والسحب والإفلات، وخصائص ARIA اللازمة لها. وتوجد هذه الوظائف في الحزمة @ui-sdk/core.

يمكن فهم السلوك من قائمة README نفسها: كيف يستجيب العنصر للمفاتيح، وأين يذهب التركيز، ومتى يُغلق، وما الخصائص التي تصفه للتقنيات المساعدة. ولا يقدم README تعريفاً نظرياً مستقلاً للسلوك، لذلك يكفي فهم الفكرة من الأمثلة: المكوّن يُبنى من وظائف مشتركة، بدل كتابة كل وظيفة من الصفر.

مثال توضيحي: فريق تقني افتراضي في جدة يملك لوحتين إداريتين، ويحتاج حقل بحث في كل منهما. يريد أن يعود التركيز إلى الحقل بعد مسح النص. إذا عُرّف هذا السلوك مرة واحدة، أمكن إعادة استخدامه في اللوحتين بدل تكرار المنطق نفسه. المثال للتوضيح فقط، ولا يصف عميلاً حقيقياً.

تنبيه: المكتبة في مرحلة beta، ويذكر README أن الإطار والواجهات والسلوك قد تتغيّر قبل الإصدار العام.

كيف تُبنى المكوّنات من سلوكيات؟

يعرض README مثالاً باسم search-field. يُعرَّف المكوّن عبر أجزاء (slots)، ولكل جزء سماته وأحداثه وشرط ظهوره الخاص.

يستخدم المثال الدالة createFocusRecovery لإعادة التركيز إلى حقل الإدخال بعد الضغط على زر المسح.

بعد التعريف، تستدعي حزمة الإطار الدالة createParts، فتُعاد أجزاء مثل Root وInput وClear. ويذكر README أن هذه الأجزاء متماثلة في الأطر الخمسة المدعومة: React وVue وSvelte وSolid وWeb Components.

الوكيل الذكي والمكوّن الواجهي: ما الفرق في العمل اليومي؟

في العمل التقليدي يكتب المطور المكوّن، ويضيف لوحة المفاتيح وإدارة التركيز وسمات ARIA بيده. أما وفق README، فيكتب الوكيل البرمجي هذه التعريفات بعد تثبيت مهارة ui-sdk. هذا وصف من المستودع، وليس ضماناً لجودة الناتج.

ترتبط ARIA بالتقنيات المساعدة، فهي تصف دور العنصر وحالته وخصائصه. ويشرح دليل ممارسات التأليف الصادر عن W3C أدوار ARIA وحالاتها وخصائصها، ويقدم أمثلة عملية لكل نمط تصميم، مع دعم لوحة المفاتيح. لذلك يبقى المراجع البشري مسؤولاً عن مقارنة ما يولّده الوكيل بهذا الدليل، واختبار المكوّن بلوحة المفاتيح قبل الإطلاق.

كيف أثبّت المكتبة وأجرّب مثالاً بسيطاً خطوة بخطوة؟

قبل إدخال المكتبة في مشروع إنتاجي، يحتاج الفريق إلى تجربة صغيرة تجيب عن سؤال واحد: هل تستحق وقت التعلّم؟ يشرح هذا القسم مساراً قابلاً للتنفيذ في مشروع معزول، وينتهي كل جزء بقائمة تحقق. لا تكشف هذه التجربة الأداء أو التوافق مع أنظمتك، لكنها تعطي الفريق نتيجة ملموسة قبل أي قرار أوسع.

تعرض الفقرات التالية الأوامر والخطوات كما وردت في المستودع، ويمكن لفريقك تكرارها ومراقبة النتيجة بنفسه.

تجهيز بيئة اختبار معزولة

أنشئ مشروعاً تجريبياً فارغاً، ولا تضف إليه بيانات حقيقية أو مفاتيح وصول. مثلاً، قد يخصص فريق تقني في شركة متوسطة جهازاً للتطوير منفصلاً، ويجرّب المكتبة عليه قبل عرض النتيجة على الإدارة.

لا يحدد README إصدار Node.js المطلوب، لذلك تحقق من متطلبات البيئة في الوثائق الرسمية، وسجّل النسخ التي استخدمتها حتى تستطيع إعادة التجربة لاحقاً.

تثبيت الحزم والمهارة

ثبّت الحزمة الأساسية ومحوّل إطارك. مع React يكون الأمر npm install @ui-sdk/react @ui-sdk/core، ولبقية الأطر استبدل @ui-sdk/react بالحزمة المناسبة كما يذكر README: @ui-sdk/vue أو @ui-sdk/svelte أو @ui-sdk/solid أو @ui-sdk/web.

بعد ذلك أضف مهارة الوكيل بالأمر npx skills@latest add vercel-labs/ui --skill ui-sdk. يعرض README هذا الأمر ضمن خطوات الإعداد، ويقول إن المطور لن يحتاج إلى كتابة هذا الكود بنفسه، وإن الوكلاء سيكتبونه. ومع ذلك يُراجَع كل ملف يُنتجه الوكيل قبل قبوله.

إنشاء مكوّن بحث بسيط وعرضه

المثال الرسمي في README هو مكوّن search-field. يعرّف حالة نصية تبدأ فارغة، ويستخدم createFocusRecovery لإعادة التركيز إلى حقل الإدخال، ويعرض زر مسح عند وجود نص. انسخه إلى ملف مستقل، ثم اعرضه في إطارك عبر createParts.

يذكر README أن الأجزاء متطابقة في الأطر الخمسة. بعد العرض تحقّق من التالي:

  • تتغير القيمة مع كل حرف تكتبه.
  • يفرّغ زر المسح الحقل، ويظهر الزر فقط عند وجود نص.
  • يعمل التنقل بلوحة المفاتيح كما تتوقع.
  • هذه الفحوص لا تكفي لتقييم الوصولية كاملة. راجع ممارسات ARIA في دليل APG الصادر عن W3C قبل أي حكم على الواجهة.

كيف أربط المكتبة بوكيل برمجي وأي أدوات تعمل معها؟

يحتاج الوكيل البرمجي إلى معرفة بالمكتبة قبل أن يكتب مكوّناً صالحاً. لهذا يقدّم المستودع مهارة (skill) باسم ui-sdk ضمن خطوات الإعداد الموصى بها في README. إذا سأل فريقك كيف أستخدم vercel labs ui مع الذكاء الاصطناعي، فالبداية هي تثبيت هذه المهارة في المشروع.

يذكر README أن المهارة تُضاف بأمر واحد، وبعدها يكتب الوكيل تعريف المكوّن. لكن الملف لا يسرد الأدوات التي تعمل مع هذه المهارة. لذلك يجب أن يتحقق الفريق من دعم أداته قبل أن يبني عليها.

مثال توضيحي: فريق تقني في شركة لوجستية بالرياض يحتاج حقل بحث مع زر مسح في لوحة داخلية. يطلب المطوّر المكوّن من الوكيل، ثم يراجعه مع زميل قبل دمجه في المشروع. هذا المثال للتوضيح فقط، وليس حالة عميل حقيقية.

  • المستودع يذكر أن المكتبة في مرحلة beta، وأن الواجهات والسلوك قد تتغيّر قبل الإصدار العام.
  • README لا يشرح كيف تتعامل كل أداة برمجية مع المهارة، لذلك تحقّق من دعم أداتك قبل الاعتماد عليها.
  • قاعدة عملية: اعتبر كود الوكيل مسودة، وراجعه كما تراجع كود أي زميل.

تثبيت مهارة ui-sdk للوكيل

أضف المهارة بالأمر الوارد في README: npx skills@latest add vercel-labs/ui --skill ui-sdk. بعد الإضافة، تأكد أن الوكيل الذي تستخدمه يقرأ المهارة فعلاً. اختبر ذلك بطلب مكوّن بسيط، وراجع هل يبدو الناتج مبنياً على تعريف بالسلوكيات.

هذا الاختبار لا يغني عن وثائق أداتك. اقرأ ما تقوله الأداة عن دعم المهارات، ثم جرّب قبل الاعتماد عليها في مشروع فعلي.

  • README يذكر حزم الإطارات: React وVue وSvelte وSolid وWeb Components. اختر الحزمة المطابقة لإطارك، واجعل الإصدار المثبّت متوافقاً معها.

تسلسل العمل من الطلب إلى المكوّن

وفق المثال في README، يعرّف الوكيل المكوّن كمجموعة سلوكيات باستخدام definePrimitive، ثم يربطه بإطارك عبر createParts. ويذكر README أن الأجزاء بالأسماء نفسها تبقى متطابقة في الأطر الخمسة.

الخطوات الدقيقة التي ينفذها الوكيل داخلياً غير موثقة في README، فقد يختلف الناتج من أداة إلى أخرى. لذلك صف السلوك المطلوب بدقة: التنقل بلوحة المفاتيح، والتركيز، وما يحدث عند الضغط على زر المسح. ثم قارن الكود بمثال README لتعرف شكله المتوقع.

ما الفرق بين هذه المكتبة ومكتبات واجهات المستخدم التقليدية؟

يمكن تمييز نهجين في بناء مكوّنات الواجهة. في الأول يكتب المطور كل مكوّن بيده، وفي الثاني تُبنى المكوّنات من سلوكيات مشتركة. هذا تمييز وصفي لأغراض المقارنة في هذا المقال، وليس تصنيفاً لكل مكتبات واجهات المستخدم.

تقدّم vercel labs ui النهج الثاني. يذكر README أن الوكيل البرمجي يكتب المكوّن بعد أن يُمنح مهارة ui-sdk، ليتعرّف على المكتبة قبل الكتابة. ويبقى الفريق مسؤولاً عن مراجعة الكود قبل اعتماده، لأن README لا يصف أي مراجعة تلقائية. الفرق هنا في طريقة العمل، ولا يعني بالضرورة فرقاً في الجودة.

أما README فيصف المكتبة بسلوكيات مثل التنقل بلوحة المفاتيح والتركيز والتحديد. وتُستعمل عبارة headless components عادةً لوصف مكوّنات تقدّم السلوك دون تصميم مرئي، لكن README لا يستخدم هذه العبارة. لذلك تحقّق من حدود الشكل المرئي في وثائق المشروع قبل أن تفترض شيئاً.

من يكتب المكوّن في كل نموذج؟

في النهج اليدوي يكتب المطور المكوّن، ويختبر التنقل بلوحة المفاتيح، ويضبط خصائص ARIA بنفسه. هذا يمنح تحكماً دقيقاً، لكنه يحمّل الفريق عبء الصيانة لكل إطار عمل يستخدمه.

في نموذج المكتبة يُعرَّف المكوّن كأساس (primitive) من سلوكيات، ويكتب الوكيل البرمجي الكود وفق المهارة المرفقة. يذكر README أن المطورين لا يحتاجون إلى تعلّم كتابة هذا الكود. هذه طريقة تقترحها المكتبة، ولا تُعفي الفريق من المراجعة.

مثال توضيحي لا يمثل عميلاً حقيقياً: شركة متوسطة تحتاج إلى حقل بحث يعمل بلوحة المفاتيح في تطبيق React ولوحة إدارية بـ Vue. في النهج اليدوي يكتب الفريق الحقلين بشكل منفصل، أما هنا فيُعرَّف الأساس مرة واحدة ثم يُعرض في الإطارين.

متى يكون النهج المعتمد على السلوكيات أنسب؟

هذا تقدير مبني على طبيعة المكتبة، لا على بيانات مقارنة. قد يكون النهج أنسب عندما يعمل الفريق على أكثر من إطار عمل، أو تتكرر العناصر التفاعلية نفسها في منتجات متعددة.

أما المشروع الصغير الذي يستخدم إطار عمل واحداً فقد يكون الكود اليدوي أبسط. والمكتبة ما زالت في مرحلة beta، وقد تتغير واجهاتها وسلوكها قبل الإصدار العام، كما يذكر README. لذلك يحتاج أي قرار إلى تجربة داخلية أولاً.

ويصف دليل ممارسات ARIA الصادر عن W3C أنماط المكوّنات مع الأدوار والحالات والخصائص ودعم لوحة المفاتيح، وهو مرجع مفيد لمراجعة أي مكوّن قبل اعتماده. وعند النظر في vercel labs ui مقارنة بمكتبات واجهات أخرى، فالسؤال الأهم ليس أيها أشهر، بل أي نهج يناسب فريقكم في الصيانة والمراجعة والإتاحة.

  • فريق يعمل على أكثر من إطار عمل واحد
  • فريق يريد مراجعة سلوك الوصول بشكل موحّد عبر المكوّنات

مقارنة بين النهجين

النهج اليدوي التقليدي

  • يكتب المطور كل مكوّن بنفسه لكل إطار عمل
  • قد يُعاد كتابة منطق لوحة المفاتيح والتركيز في كل مكوّن
  • يراجع الفريق خصائص ARIA في كل مكوّن على حدة
  • يبقى التحكم الكامل في الكود والتصميم

النهج المعتمد على السلوكيات

  • تُعرَّف السلوكيات مرة واحدة في @ui-sdk/core
  • يبني الوكيل البرمجي المكوّن باستخدام مهارة ui-sdk
  • تُعرض الأجزاء نفسها في React وVue وSvelte وSolid وWeb Components
  • يحتاج الكود المولَّد إلى مراجعة من الفريق قبل الوصول إلى الإنتاج

ما القيود والمخاطر قبل الاعتماد عليها في مشروع إنتاجي؟

قبل إدخال مكتبة vercel-labs ui في مشروع يخدم عملاء فعليين، يحتاج الفريق إلى معرفة ما لا تغطيه المكتبة وما قد يتغيّر فيها. يذكر README أن UI SDK في حالة beta، وأن الإطار والواجهات البرمجية والتوثيق والسلوك قد تتغيّر قبل الإصدار العام.

بحسب README، تتولى @ui-sdk/core التنقل بلوحة المفاتيح والتركيز والتحديد والإغلاق والنوافذ المنبثقة والسحب والإفلات وARIA اللازم لها. أما التصميم البصري والمحتوى والتحقق من البيانات فلم يذكرها المستودع، فيخطط لها الفريق.

ما الذي قد يتغيّر في مرحلة beta؟

حالة beta تعني أن الاستقرار غير مضمون، ويخضع الاستخدام لشروط beta الخاصة بـ Vercel. لم نجد في المصادر موعداً للإصدار العام، ولا يمكن تقديره من المستودع.

  • أسماء الدوال والمعاملات، مثل createParts، وشكل الواجهة البرمجية نفسها.
  • سلوك المكوّنات، فقد تختلف النتيجة بعد ترقية الإصدار.
  • التوثيق، فقد لا يطابق ما تراه في الكود بعد التحديث.
  • ثبّت الإصدار في package.json، وراجع ملاحظات كل إصدار قبل الترقية.

أثر الكود المولّد بواسطة الوكلاء على الجودة والأمان

يذكر README أن الوكلاء سيكتبون المكوّنات بدلاً من المطوّر. هذا وصف لطريقة عمل المكتبة، وليس ضماناً لجودة النتيجة، فتبقى المراجعة مسؤولية الفريق.

الكود المولّد قد يعمل في العرض السريع ثم يخفق عند اختبار لوحة المفاتيح. مثال توضيحي لا يمثل عميلاً حقيقياً: فريق في شركة توزيع بالرياض طلب من وكيل بناء نموذج بحث، فعمل الحقل بالفأرة، لكن المستخدم لم يصل إلى زر المسح بلوحة المفاتيح. هذه من مخاطر الكود المولّد بالذكاء الاصطناعي.

  • راجع كل مكوّن مولَّد قبل دمجه في الفرع الرئيسي.
  • اختبر التنقل بلوحة المفاتيح والتركيز بعد كل تغيير.
  • عند اكتشاف ثغرة أمنية، اتبع SECURITY.md ولا تفتح issue علنياً.

قائمة تحقق قبل قبول المكتبة في المشروع

عند تقييم مكتبة مفتوحة المصدر، لا تكفي النجوم والشوك. تذكر بيانات GitHub أن الرخصة Apache-2.0، لكنها لا تدل على جودة الصيانة، لذلك افحص سجل الالتزامات والإصدارات بنفسك. ويطلب قسم تطبيق الرخصة تضمين نسخة منها في العمل، عادةً في ملف باسم LICENSE.

يقدّم دليل ARIA Authoring Practices Guide أنماطاً وأمثلة لدعم لوحة المفاتيح، فيصلح مرجعاً للاختبار. لكنه لا يضمن أن مكوّناتك مُتاحة، والاختبار على مكوّناتك يبقى ضرورياً.

القائمة التالية نقطة بداية، ولا تغني عن مراجعة قانونية وأمنية داخل شركتك.

قائمة تحقق قبل قبول المكتبة

كيف أتحقق من الترخيص والصيانة والأمان قبل تبنّي المكتبة في شركتي؟

قبل تبنّي أي مكتبة يحتاج الفريق إلى إجابات عن ثلاثة أسئلة: ما الذي تسمح به الرخصة؟ هل المستودع نشط؟ وكيف يُبلَّغ عن ثغرة؟ مثال توضيحي: مدير تقنية في شركة توزيع بجدة يكلّف مهندساً بتوثيق هذه الإجابات مع سجل القرار.

ماذا تقول الرخصة وماذا لا تقول؟

بحسب بيانات GitHub التي اعتمدنا عليها، مستودع vercel-labs/ui مرخّص بـ Apache-2.0. تحقّق بنفسك من وجود ملف LICENSE في المستودع، وقارن نصه بالنص المنشور على موقع Apache، واحفظ نسخة منه مع وثائق المشروع.

تنظّم الرخصة شروط الاستخدام وإعادة الإنتاج والتوزيع، وتنص على توزيع البرنامج «AS IS» دون ضمانات أو شروط من أي نوع. فهي لا تعني أن المكتبة مناسبة لاحتياجك.

أما الاعتماديات فلم تتناولها النصوص التي اعتمدنا عليها، فلا نفترض أن ترخيص المكتبة يغطيها. اطلب فحص رخصها بأداة معتمدة لدى فريقك، وراجع المتطلبات التعاقدية أو التنظيمية مع الفريق القانوني، لأن القواعد قد تختلف بحسب الجهة والدولة.

كيف أقيّم نشاط الصيانة بنفسي؟

يصف README المكتبة بأنها في مرحلة beta، وينص على أن الإطار والواجهات البرمجية والتوثيق والسلوك قد تتغير قبل الإصدار العام. لذلك تحتاج متابعة صيانة مكتبة مفتوحة المصدر إلى مراجعة متكررة لا قراءة واحدة.

خطوات تحقق مختصرة للرخصة والصيانة والأمان

متى لا تكون هذه المكتبة الخيار المناسب؟

ليست مكتبة vercel-labs ui خياراً مناسباً لكل مشروع. أول ما يجب فحصه هو مرحلة النضج، فالمستودع يصف UI SDK بأنها في مرحلة beta، وأن الإطار والواجهات البرمجية والتوثيق والسلوك قد تتغيّر قبل الإصدار العام. لذلك يبدأ القرار بسؤال «متى لا تستخدم مكتبة beta؟» قبل أي سؤال عن المزايا.

لنأخذ مثالاً افتراضياً: شركة لوجستية في جدة تريد تحديث لوحة تتبّع الشحنات التي يستخدمها موظفو خدمة العملاء طوال اليوم. إذا كان أي تغيير في سلوك حقل البحث أو القائمة المنسدلة قد يعطّل العمل، فالتأجيل أو الاكتفاء بمكتبة مستقرة أسلم من تحمّل تغيّرات لم يطلبها الفريق. هذا الحكم يزداد وضوحاً في المشاريع الإنتاجية التي تخدم عملاء فعليين.

حالات يكون فيها التأجيل أفضل

تُعد الحالات التالية مؤشرات واضحة على أن الوقت الحالي غير مناسب للتبنّي:

  • مشروع إنتاجي حساس لا يحتمل تغيّر الواجهات قبل اختبار كامل.
  • فريق لا يملك عملية مراجعة كود. يذكر المستودع أن الوكلاء هم من يكتبون المكونات، ومن يراجع الناتج يحتاج قدرة على فحصه.
  • إطار غير مدعوم. تذكر الوثيقة محولات لـReact وVue وSvelte وSolid وWeb Components فقط.
  • حاجة إلى توثيق مستقر ومكتمل لكل حالة استخدام، لأن التوثيق نفسه قد يتغيّر.
  • سياسة داخلية لم تراجع شروط الاستخدام. الرخصة Apache-2.0، لكن المكتبة تخضع أيضاً لشروط بيتا Vercel، فيجب قراءة الاثنين معاً.

بدائل للتقييم قبل القرار

إذا تحقق أحد هذه الشروط، فلا يعني ذلك رفض المكتبة نهائياً. يمكن أن يكون التقييم على مراحل:

  • جرّب المثال الرسمي في فرع منفصل، ولا تنقله إلى بيئة الإنتاج.
  • اختبر أي مكوّن، سواء كتبه مطوّر أو وكيل برمجي، بمعيار ثابت مثل أنماط ARIA ودعم لوحة المفاتيح الواردة في دليل الممارسات الذي تنشره W3C.
  • قارن المكتبة مع خيار مستقر يدعم إطارك، واكتب معايير القرار قبل بدء المقارنة.

أسئلة شائعة

ما هي مكتبة vercel-labs ui؟

مكتبة vercel-labs ui، واسمها في README «UI SDK»، وصفها المستودع بأنها «مكتبة سلوكيات يستخدمها الوكلاء الذكيون لبناء الجيل التالي من واجهات المستخدم». تُكتب بلغة TypeScript وترخيصها Apache-2.0. تُبنى المكوّنات فيها من سلوكيات مثل التنقل بلوحة المفاتيح والتركيز والتحديد، ثم تُربط بأطر العمل المختلفة.

هل مكتبة vercel-labs ui مستقرة للاستخدام الإنتاجي؟

يصف README المكتبة بأنها في مرحلة beta، وأن الإطار والواجهات البرمجية والتوثيق والسلوك قد تتغيّر قبل الإصدار العام. وتخضع لشروط beta الخاصة بـ Vercel. لذلك ينبغي تجربتها في مشروع منفصل وتقييمها قبل إدخالها في أي مشروع يخدم عملاء فعليين.

كيف أثبّت @ui-sdk/react مع @ui-sdk/core؟

وفق README، يُنفَّذ الأمر: npm install @ui-sdk/react @ui-sdk/core. ولإطار آخر يُستبدل @ui-sdk/react بـ @ui-sdk/vue أو @ui-sdk/svelte أو @ui-sdk/solid أو @ui-sdk/web. بعد التثبيت، تُضاف مهارة الوكيل بالأمر npx skills@latest add vercel-labs/ui --skill ui-sdk. ويُفضَّل تنفيذ ذلك في مشروع تجريبي منفصل.

ما المقصود بالسلوكيات (behaviors) في UI SDK؟

السلوكيات هي الطبقة التي تتولى ما يتوقعه المستخدم من عناصر الواجهة، مثل التنقل بلوحة المفاتيح والتركيز والتحديد والإغلاق والنوافذ المنبثقة والسحب والإفلات، إضافة إلى خصائص ARIA اللازمة لها. وفق README، تعيش هذه الوظائف في @ui-sdk/core، ثم تُربط بمحوّلات لخمسة أطر هي React وVue وSvelte وSolid وWeb Components. وهذا يعني أن المكوّن يُبنى من هذه السلوكيات الجاهزة بدلاً من كتابتها من الصفر.

ما الرخصة التي يذكرها المستودع؟

يذكر المستودع ترخيص Apache-2.0. ومعنى ذلك أن نص هذا الترخيص هو المرجع فيما يُسمح به من استخدام وتوزيع. يُنصح بمراجعة نص الترخيص نفسه في المستودع، وإحالة السؤال إلى الفريق القانوني قبل الاعتماد، لأن هذا المقال لا يحدد التفاصيل القانونية.
